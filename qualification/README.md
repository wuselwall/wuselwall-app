# Candidate accessibility and UI qualification

The [qualification design](../specs/accessibility-and-ui-qualification.md) is implemented
as a manually dispatched evidence suite and an enforced app/server release gate. The shared
inventory contains 72 states and accounts for every release route. Two exclusions are
checked against the production router: the legacy settings redirect and the developer-only
diagnostics page. Route coverage does not mean every dialog, permission state or backend
journey has been exercised.

A successful **full comparison** run produces `READY_FOR_REVIEW`, never an automatic claim
of accessibility conformance. Its summary retains `qualified: false`: baseline acceptance
and physical-device review belong to a person approving the protected release environment.
Capture, smoke, canonical-only, partial, skipped and failing runs cannot authorize release.

## What runs

- Flutter: bundled fonts, four locales, Android/iOS widget adaptations, light/dark and
  kiosk night, semantics, labels, target sizes and rendered text contrast. The responsive
  tier adds relevant widths, 599/600/601 boundaries and 100/200% text. Every inventory
  state runs regardless of changed paths. Fixture integrity checks render all 43 direct
  destination fixtures in four languages before their audit results can count.
- Browser: the release-compiled synthetic-data entry point, stable screenshots and ARIA
  snapshots, axe-core DOM/ARIA checks, console/page errors and blocked external requests.
  Chromium runs the broad matrix; Firefox/WebKit are optional focused compatibility runs.
- Native: real Flutter accessibility nodes audited through Android ATF and iOS XCTest,
  phone/tablet rendering captures, large-text profiles, detector and keyboard checkpoints,
  plus PNG and semantic comparison against a separate native baseline. Android and iOS
  execute sequentially on a native macOS runner. Nine required profiles include four base,
  four enlarged-text and an Android minimum-supported-API phone. Required case IDs are
  generated by `qualification/native/report.mjs`.
- Production entry point: a release web build of `lib/main.dart`, exercised through server
  discovery, encrypted-storage migration and the shopping journey using intercepted APIs.
  This is separate from fixture captures and does not establish real backend authentication
  or the behavior of a signed store binary.
- Detector/integrity tests: deliberately bad contrast (SDK and exact audit), a small
  unlabeled action and an unlabeled HTML button must be detected; the exact audit's controls
  reproduce the SDK's border misattribution and keep mixed paint undecided. Baseline tests reject altered/missing/extra
  files, invalid archives and mismatched environments. Missing native nodes, detector
  results, screenshots or required profiles fail the native report.

Expanded tests live outside `app/test/`; ordinary `flutter test` does not discover them.
`candidate-evidence` has only `workflow_dispatch`. Existing fast CI checks retain their
schedule. Android, iOS and server releases containing the web archive now require successful
qualification for that exact commit and protected human approval before publishing/signing.
Separate backend/recovery checks remain part of the release checklist; operator-run local
deployment utilities are independent.

Expanded Linux validation rendered all 180 direct fixtures and executed the earlier
70-state, 8,760-case Flutter matrix. It exposed accessibility findings and large-text layout defects. After
fixing those layouts and calendar targets, a 672-case responsive rerun had no framework,
label or target-size findings; the contrast findings of that sweep were the SDK's border
misattribution, resolved by the exact audit described below. The ordinary
suite passed 1,574 tests, with seven backend integration tests intentionally skipped without
backend configuration. Those seven require the separate disposable-backend CI job. Android
app and instrumentation APKs compile; native device execution and the iOS audit build still
need validation on provisioned macOS devices. No native baseline has been approved by these
local checks.

Text contrast is decided per paragraph by an exact audit (`qualification_test/exact_contrast.dart`)
wherever paint is unambiguous, and by the raw Flutter SDK guideline everywhere else. The SDK
guideline estimates both colours from a histogram of the text's box inflated by four pixels and
takes the most frequent colour below the average lightness as the text; beside 12 px text, a
table border, a cell tint or a button outline has more pixels than the glyphs' solid cores, so
the guideline reported those borders against the paper (ratios near 1.3) across the timetable,
calendar and settings. The exact audit takes the foreground from the resolved `TextStyle` and
samples the glyph boxes inflated by one pixel. Backgrounds are plateaus: colours with at least
2 % of the sample whose pixels mostly sit among pixels of the same colour (anti-aliasing never
forms one, however many pixels share a stem's coverage value). A pixel is explained when it is a
plateau or a straight blend between the ink and a plateau; the text sits on a plateau when such
ink pixels touch it, so a line box poking past an avatar's circle onto the paper does not put the
letter on the paper. The measurement is accepted when at least 96 % of the pixels are explained
and the text is visible; the ratio is the worst over the plateaus the text sits on (at most two);
translucent text is measured as its colour composited onto each; a fade counts only while the
text actually overflows; icon-font glyphs are graphics, not text, and leave no row. Gradients,
overlapping paint, opacity, animated opacity, active fades, shaders, filters, painted or shadowed
text, inline widget spans and fallback geometry stay `UNDECIDED`: the SDK verdict stands for
those nodes. A node whose every paragraph is a decided `PASS` supersedes the
SDK's estimate for that node; a decided `FAIL` is a finding (`exactTextContrast`) even where the
SDK passed. A node whose every paragraph lies under a shader mask (`EdgeFade`, the scrolling
row's edge fade) is outside the automated check's scope (text over a gradient, see the spec's
scope table): an SDK estimate there is kept in `reviewTextContrast` for a person to look at
and does not fail the case. Each case records `sdkTextContrast` (the raw SDK result),
`exactTextContrast` (every paragraph with colours, ratio, requirement, effective size, weight,
coverage and the superseded SDK blocks), `reviewTextContrast` and the older render-tree paint
diagnostic. The controls in
`exact_contrast_test.dart` prove a real failure fails, that readable text in a bordered table
reproduces the SDK misattribution and is proven exact, that two backgrounds and translucent text
are decided by their worse and composited colours, and that a gradient, an opacity and an
overflowing fade stay undecided.
The Flutter job writes `contrast-report.json` and `contrast-report.md` even when the matrix
fails. They group repeated labels, ratios and reported colours while preserving case IDs,
unparsed findings and an input checksum. The report grants no waivers.

Bundled Noto Sans Symbols covers the shipped arrow glyphs. Web's automatic fallback font
base is also restricted to this installation's own origin. This does not supply every
Unicode script: unbundled characters in names or imported calendar text may remain missing
until the installation serves the corresponding reviewed local font pack. Baseline
fingerprints include bundled font-file checksums on both web and native platforms.
`qualify:font-policy` exercises unsupported CJK input and asserts that fallback requests
stay on the local origin; it does not certify the rendering of those characters.

## Select the candidate

Dispatch from the default branch with its current full commit SHA. Preparation checks that
the entered SHA matches the immutable event SHA and belongs to default-branch ancestry
before candidate code executes. Every job checks out that SHA. A later branch advance does
not change the tested commit. Local runs can exercise a branch before merge; this workflow
cannot select an arbitrary historical commit.

The workflow disables Actions cache access (`cache-mode: none`), tool-action caches and
persisted checkout credentials. Baseline downloads happen before candidate scripts, and
their token is absent during extraction/testing. Run reviewed candidate commits on dedicated
CI accounts without signing credentials, production data or family accounts. Persistent
runner files still require isolation. See
[GitHub's cache access controls](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#cache-mode).

## Run locally

From the repository root, install locked npm packages and resolve app dependencies with
the pinned Flutter SDK. Fixture tests need no backend or credentials.

```sh
npm ci
cd app
flutter pub get --enforce-lockfile
cd ..
npm run qualify:check
cd app
flutter test --no-pub qualification_test --dart-define=QUALIFY_MATRIX=smoke
cd ..
npm run qualify:build-web
npx playwright install chromium
npm run qualify:pixel-controls
npm run qualify:scroll-controls
npm run qualify:font-policy
QUALIFY_MODE=capture QUALIFY_MATRIX=smoke npm run qualify:web
```

Profiles are `smoke`, `canonical`, `responsive` and `full`. Workflow choices omit standalone
`responsive`; `full` includes it. Canonical coverage contains 580 browser cases and 1,160
Flutter cases before detectors. Full coverage has 2,512 browser and 8,888 Flutter cases. Flutter's responsive
tier additionally crosses 100/200% text and both widget platforms. Native smoke uses
German/light; full uses all four locales/light/dark. Smoke is diagnostic only.

Browser output lives in `build/qualification/web/` (HTML report, JSON and failure traces),
unapproved images/semantics in `build/qualification/capture/`, Flutter findings in
`build/qualification/flutter/<profile>/results.json`, native evidence in
`build/qualification/native/`, and production-entry evidence in `build/qualification/production/`.
The aggregate is `build/qualification/summary.json`. A missing report fails aggregation.

To group an existing full-matrix diagnostic report locally, from the repository root:

```sh
node qualification/contrast-report.mjs build/qualification/flutter/full/results.json build/qualification/flutter/full
```

Browser semantics are enabled from launch; a separate test-only readiness signal is emitted
after the real destination renders. If axe reports a target clipped by a scroll viewport,
the audit scrolls with real input and checks the same DOM node fully inside every clipping
ancestor before accepting its size. Initial and follow-up audits and geometry are retained.
Unreachable, replaced or genuinely undersized controls remain failures, as do all other axe
findings. `qualify:scroll-controls` checks those boundaries independently.

Rules fail their tests; existing findings are not suppressed. Flutter's histogram-based
contrast checker can misread image/text regions: review the rendered pixels and fix actual
problems instead of lowering the global threshold. axe's DOM colour rule is explicitly
unsupported for Flutter's canvas, and its report records this limitation. ATF may report
contrast as `NOT_RUN` for some virtual nodes; the Flutter contrast gate remains required.

Optional browser compatibility coverage:

```sh
npx playwright install firefox webkit
QUALIFY_BROWSERS=chromium,firefox,webkit QUALIFY_MODE=capture QUALIFY_MATRIX=canonical npm run qualify:web
```

The fixture entry point uses a fixed Dart clock, locale, browser timezone and in-memory
providers. Direct route fixtures compose the real destination widgets; production route
guards and authentication remain journey-test concerns. The email-code capture uses the
stable resend state. The pairing capture freezes the persistent waiting spinner only after
the actual code and QR content exist. Neither changes the production entry point. Regenerate
shared destination predicates/native metadata with `node qualification/generate-native.mjs`
when extending the inventory; `qualify:check` rejects stale output.

## Review and compare baselines

Capture the full intended profile in its fixed environment. Inspect all destinations,
images, semantic changes, findings and missing coverage. Resolve accessibility failures;
visual acceptance cannot waive them. Preserve a copy for review rather than editing the
approved baseline in place.

For web, seal the copied capture directory with its exact source commit:

```sh
node qualification/baseline.mjs seal /tmp/reviewed-web-baseline <full-source-sha>
QUALIFY_BASELINE_DIR=/tmp/reviewed-web-baseline \
QUALIFY_BASELINE_SHA256=<reviewed-web-manifest-sha256> \
QUALIFY_MODE=compare QUALIFY_MATRIX=full npm run qualify:web
```

Sealing records file digests and environment information; it does not approve the content.
Review the manifest digest separately and keep the accepted digest in version control.
Web comparison verifies every file before launching the browser. It uses a measured
perceptual threshold of 0.04 and permits zero pixels above that threshold. The repeatability
probe found only emoji resampling noise (maximum RGB channel delta 9/255);
`npm run qualify:pixel-controls` proves that this noise passes and a real colour change
fails. Semantic files use `-aria.yml`, matching Playwright's snapshot normalization.

Native captures are collected and sealed under `build/qualification/native/capture/`.
Copy the reviewed directory, preserving its manifest/environment, then explicitly reseal
it with the source SHA:

```sh
node qualification/native/baseline.mjs seal /tmp/reviewed-native-baseline <full-source-sha>
QUALIFY_CANDIDATE_SHA=<full-candidate-sha> \
QUALIFY_MODE=compare \
QUALIFY_NATIVE_BASELINE_DIR=/tmp/reviewed-native-baseline \
QUALIFY_NATIVE_BASELINE_SHA256=<reviewed-native-manifest-sha256> \
bash qualification/native.sh
```

Native comparison requires exact decoded RGBA pixels and exact semantic snapshots until
repeatability measurements justify a separately reviewed tolerance. Its environment binds
Flutter/engine/Dart, Xcode, macOS, iOS runtime build, Android image/emulator, inventory and
per-profile display/text metrics. The web tolerance does not apply to native images.

Publish reviewed bundles as `web-baseline.zip` and `native-baseline.zip` on the same
separate `ui-baseline-*` GitHub Release. Each archive root contains `manifest.json` and its
browser/profile directories; zip the contents, not their parent. Comparison dispatch takes
`baseline_tag`, `baseline_sha256` and `native_baseline_sha256`. Missing, changed or
cross-environment snapshots fail; normal comparisons never create/update approved images.
Toolchain, OS/runtime, renderer or inventory changes require reviewed baseline migration.

Baseline publication and approval are explicit operator actions. Keep approved bundles and
accepted release evidence durably; ordinary Actions artifacts expire after 30 days.

## Provision the native runner

Use a native ARM64 macOS Actions runner with pinned Xcode/iOS Simulator runtime, CocoaPods,
Android command-line SDK/emulator, platform tools and ARM64 system images. On Apple Silicon,
run the Actions runner, Flutter, JDK and Android tools natively, without Rosetta. Use CI-only
AVDs with no family accounts/data. Install the SDK/platforms required by `app/android/`.
The qualification job supplies native ARM64 Flutter, Node and Java; device provisioning
is separate. The [native provisioning runbook](native/README.md) describes pinned SDKs,
three CI AVDs and an explicitly selected iOS runtime. Its opt-in installer prints a dry-run
plan by default; `bash qualification/native/provision.sh --apply` performs installation
only after the required version/build and license decisions are supplied.

Run the read-only diagnostic workflow **Native qualification preflight**, or:

```sh
bash qualification/native/preflight.sh
```

It records architecture/tool/runtime/AVD diagnostics and fails for unavailable prerequisites.
Inspect `xcrun simctl list runtimes`, `xcrun simctl list devicetypes` and
`emulator -list-avds`, then set repository variables:

| Variable | Meaning |
|---|---|
| `QUALIFICATION_IOS_RUNTIME` | Exact installed CoreSimulator runtime identifier, supporting XCTest accessibility audits |
| `QUALIFICATION_IOS_PHONE_TYPE` | Optional phone type; defaults to iPhone 16 |
| `QUALIFICATION_IOS_TABLET_TYPE` | Optional tablet type; defaults to 11-inch iPad Pro M4 |
| `QUALIFICATION_ANDROID_PHONE_AVD` | Pre-provisioned ARM64 phone AVD |
| `QUALIFICATION_ANDROID_TABLET_AVD` | Pre-provisioned ARM64 tablet AVD |
| `QUALIFICATION_ANDROID_MIN_PHONE_AVD` | Pre-provisioned ARM64 phone at the app's minimum supported Android API |

Set `ANDROID_HOME` in the runner environment. The script checks acceleration, creates
disposable iOS devices, uses read-only Android AVDs on a dedicated unused port and cleans
up only its own devices/processes. It runs all required profiles even after one fails and
preserves JSON, native logs and `.xcresult`. Large profiles use iOS accessibility text size
or Android 200% font plus larger display density. Pinned profile/runtime/image changes need
baseline review. Unsupported platform audit capabilities remain explicit in reports.

For diagnosis, select one profile, for example `bash qualification/native.sh android-phone`.
A complete run uses `bash qualification/native.sh` with `QUALIFY_CANDIDATE_SHA` and
`QUALIFY_MODE=capture|compare`. Do not run this lane in a macOS container. Optional Linux
Android acceleration needs proven `/dev/kvm` access and its own baseline environment.

## Configure and use release promotion

Create the GitHub environment **release-promotion**, configure at least one required
reviewer, and disable administrator bypass. The read-only promotion guard rejects missing
or weaker protection. Keep distribution signing credentials in protected release jobs.

1. Review a baseline capture and publish both immutable baseline bundles/digests.
2. Dispatch `candidate-evidence` on the default-branch candidate SHA with `matrix=full`,
   `mode=compare` and both reviewed manifest digests.
3. Resolve every failed/missing/flaky result. A source change requires a new candidate run.
4. Review the successful run's reports, baseline changes and physical-device checklist.
5. Tag that exact tested commit or manually dispatch the app/server release for that commit.
   Its guard verifies the workflow identity, source repository/default branch, exact SHA,
   full comparison verdict, required jobs and downloaded summary artifact digest. The
   signing job then waits for the environment reviewer's acceptance.

The summary says `READY_FOR_REVIEW` only when all automatic requirements pass, with
`qualified: false` and the two remaining human gates. Successful automation alone cannot
publish. An expired/corrupt evidence artifact, capture-only run, missing native audit,
unreviewed baseline or changed commit blocks promotion. Simulator/instrumented artifacts
are not the signed store artifacts: retain signed-build/device smoke and the separate
backend, security, recovery and publication checks in the
[release checklist](../specs/release-checklist.md).
